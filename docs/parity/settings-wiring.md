# Settings wiring audit

Every switch/select/radio of `crates/phoenix-app/src/ui/settings/pages.rs`:
where its value is stored and what it changes in the UI.

* Synced fields come from the protobuf descriptors of the 2026 web client
  (`discord_protos.discord_users.v1.PreloadedUserSettings.*`, local Discord
  cache, `web.*.js`). Table: `ui/settings/synced_map.rs` (read with
  `proto_read`, written with `SettingChange::Path`, merge-appended to the
  current blob so unknown fields survive).
* Local controls (client keeps them in localStorage / native settings) live
  in `LocalPrefs::ui` (`~/.config/discord-phoenix/settings.json`).
* REST routes: consents (`/users/@me/consent`) and e-mail preferences
  (`/users/@me/email-settings`). Application Test Mode is session-only in the
  client too.
* Sources (2026-11-24): every "local prefs" row was checked against the
  client's settings definitions (chunk `52b6e35…`, module 253932 maps the
  `U.*` settings to proto paths): Accessibility / StreamerMode /
  NotificationSettings / native stores stay local; the values shown by the
  live client were read through CDP without toggling anything.
* Testing never touched the user's account: unit tests encode/decode the
  blob offline (`phoenix-api` `path_changes_roundtrip`, `synced_map` tests);
  the mock backend applies patches in memory.

## Own presence (gateway op 3)

Source: web.js module 225123 (`ConnectionStore`, presence committer `H`), 894768 (`SelfPresenceStore`), LocalActivityStore and 685396 (custom status activity), socket `presenceUpdate(status, since, activities, afk)`.

* ✅ IDENTIFY keeps `status: "unknown"` like the client; the real presence goes out as op 3 right after READY (`H.update()` at the end of the READY handler) and again on every RESUMED (`H.forceUpdate()`). Before this, Phoenix never sent op 3 after identifying, so friends saw the account offline.
* ✅ Status comes from settings proto 1, field 11.1 (`status.status`); empty or `unknown` means `online`.
* ✅ Custom status (field 11.2) is sent as `{"name":"Custom Status","type":4,"state"?,"timestamps"?:{"end"},"emoji":null|{"id","name","animated"},"metadata":{}}`, plus `details` and `metadata.label` when field 11.2.6 is set. It is dropped once `expires_at_ms` has passed, and no activity is sent while invisible.
* ✅ Resent when USER_SETTINGS_PROTO_UPDATE (type 1, partial or full) changes the status or the custom status, and when the status picker or the custom status modal changes them. `self_presence` tests cover the payloads.
* ✅ Idle and AFK (IdleStore 885576): idle after 10 min without input (`6e5`), sent as `status: "idle"` (only when the chosen status is online) with `since` = last input; `afk: true` after min(`voiceAndVideo.afkTimeout` (field 5.6, default 60 s), 10 min), always when it is 0. Back to online on the next input. Phoenix reads this from Wayland `ext_idle_notifier_v1` (input notifications on v2, so idle inhibitors are ignored like the client's system idle time) on its own connection (`idle.rs`). `org.freedesktop.ScreenSaver.GetSessionIdleTime` answers NotSupported on KDE Wayland. ✅ screen lock (IdleStore `lock-screen` / `unlock-screen`: idle and AFK at once, back on unlock): Phoenix reads logind's `LockedHint` on its own session (`GetSession("auto")`, polled every 10 s like the client's 10 s system-idle poll, `idle::watch_lock`), and `self_presence::effective_idle` reports `since` = lock time and `afk: true` while locked (test `a_locked_screen_is_idle_and_afk_at_once`). Suspend needs no extra handling: the process is frozen and logind sets `LockedHint` before sleep on KDE. ❌ no X11 fallback for the input idle timer (no XScreenSaver binding).

## Settings proto writes

Source: web.js module 594061 (`updateAsync`, `markDirty`, `persistChanges`), 159201, delays `INFREQUENT_USER_ACTION` 0 / `FREQUENT_USER_ACTION` 10 / `SLOW_USER_ACTION` 20 / `AUTOMATED` 30 s.

* ✅ The client PATCHes only the categories it changed (a copy of the whole category, for example `status` = field 11), and merges every pending change into one `protoToSave`. Phoenix now does the same: every settings-proto 1 write goes through `RestClient::edit_settings_proto`. Edits made while a write is in flight (or waiting on a 429) are merged into the next GET + PATCH, and only the changed top-level fields are sent (`proto_delta`).
* ✅ Status change (status picker) = `updateAsync("status")`: field 11 with the new `status`, `status_expires_at_ms` 0 and `status_created_at_ms` kept when the status is the same (else now). The custom status (11.2) is copied byte for byte. Before this, the picker used the legacy `PATCH /users/@me/settings` with `custom_status: {text}`, which dropped the emoji and the expiry. Test `status_change_only_writes_the_status_category_and_keeps_the_custom_status`.
* No code path writes the settings proto by itself: USER_SETTINGS_PROTO_UPDATE only GETs the settings again. The 429s on 26/11 at 16:18 (6 retries, so at least two PATCHes) were a burst of user writes (custom status, toggles or a rail drop), each a GET + full PATCH with no merging.

## Soundboard

The [Soundboard support guide](https://support.discord.com/hc/en-us/articles/12612888127767) describes the local volume, global and per-server entrance sounds, and joining without playing an entrance sound. The provided Windows reference at 100% shows 40 px fields, a full-width server selector and a 321 px sound selector.

The Discord web client stores volume as a fixed32 float inside `audioContext.soundboardSettings` (category 5, field 9). Entrance preferences use the guild settings map (category 3, map field 1), with `joinSound` at field 6. Map key zero is the global default. The voice effects module (458976 in the web client bundle inspected for this change) sends the configured sound through `POST /channels/{channel_id}/custom-call-sounds` after connecting.

The settings UI was exercised on Windows with the mock backend. Live playback and account synchronization remain to be checked in a real voice channel.
